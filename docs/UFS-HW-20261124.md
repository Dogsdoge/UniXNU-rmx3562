## 2. ★ 策略修正：底层抄 HakiOS，上层抄 UniXNU

原计划（SHENGUFS-MT6895-PLAN）：fork ShengUfs → 改硬件常量。
**修正**：ShengUfs 是 SM8550 高通专用（0x1d84000 + 高通 SMMU stream 0x60），
硬件模型跟 MT6895 差异大；而 **HakiOS 的 redwood_ufshc.c 已经在 MT6895 上实机验证了 UFS READ(10)**。

新的最优组合：
| 层 | 来源 | 理由 |
|---|---|---|
| UFS 控制器底层（寄存器/传输列表/READ10/WRITE10） | **HakiOS redwood_ufshc.c**（59KB，同芯片验证） | 硬件地址/时序已验证，抄过来即可 |
| extent 映射层（文件块→裸 LBA） | ios-fuxi 0088（fx_map） | 已有设计稿 |
| IOKit IOMedia 发布（ADT→APFS 挂载链） | **UniXNU RootPublication.h / NativeUfs.cpp** | 这是 UniXNU 根卷机制的必需部分 |

⇒ 实际是"三层拼接"：HakiOS 底层 + extent 映射 + UniXNU 发布层。
不是单纯 fork ShengUfs，也不是单纯用 HakiOS。

## 3. 关键差异提醒

- HakiOS redwood_ufshc.c 是 C（BSD 风格），UniXNU 是 C++（IOKit）→ 需要包一层 C++ wrapper
- HakiOS 的 UFS 初始化依赖 LK 已把 controller/PHY/link bring up（"LK already brings up PHY/clocks/link"）
  → 在 UEFI 路线上，UEFI 的 MT6895Pkg 必须同样先初始化 UFS（CrackerCat 的 MT6895Pkg 有 UFS DXE）
- UniXNU 的 verified-root 校验 APFS 卷签名 → 我们的自造镜像可能要关（apollo 就没启用 VerifiedRoot）
